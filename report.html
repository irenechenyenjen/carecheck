2. Motivation

Where the idea came from

The idea came from my grandmother. Friends often forward her health tips and home remedies that sound convincing at first, but become unreasonable when examined more closely. Because the message comes from someone she knows and trusts, she is more likely to believe it. By the time our family notices the message, the belief may already be established and difficult to change.

Who has this problem?

CareCheck is designed for older adults who receive health advice through personal messages, especially when the trust attached to the sender makes the advice feel reliable. It also supports family members who want to raise a concern respectfully instead of simply saying that the message is wrong.

How is it handled today?

In this situation, family members may only notice the claim after it has already been read and accepted. They then have to explain why it is questionable, find reliable information, and avoid making the conversation feel like a personal correction. CareCheck is intended to create an earlier, gentler point for checking the message.

What does it cost?

This problem can cost time, create frustration during family conversations, and—when a dangerous claim is believed—create a risk that appropriate medical advice is delayed. I have not measured these costs with a formal study, so this report does not assign invented dollar or time values to them.

3. What is new here

CareCheck does not claim to be the first health-information checker. Existing search engines, health websites, fact-checking services, ChatGPT, and medical professionals can all help people evaluate health information. The project’s difference is the focused interaction and safety framing.

Existing optionWhat it offersWhat CareCheck does differently
Web searchMany results and sources.Starts from the exact forwarded message and gives one understandable first explanation.
General chatbotFlexible conversation.Uses a constrained five-level output, explicit next step, and safety boundary for this task.
Binary fact-checkQuick true/false-style judgment.Separates dangerous, incomplete, useful, uncertain, and broadly correct claims.
ClinicianProfessional context and care.Provides a low-friction pause before a user decides what to ask a clinician; it does not replace one.

The innovation is therefore not a new medical database. It is an older-adult-oriented workflow that turns a forwarded message into a calm explanation and a safer human next step.

4. The agents

Agent architecture

The current app uses one model-backed evidence-review agent, surrounded by deterministic application logic. It is not a multi-agent system.

User pastes message→Dash callback→Evidence-review agent→Safety + label gates→Result card

What the agent does

  • Reviews the health claim.
  • Assigns one of five exact levels: High caution, Mostly correct, Looks useful, Needs checking, or Unable to verify.
  • Produces a summary, explanation, next step, sources, and tool label in structured JSON.

Tools and handoffs

The agent has no autonomous external tool-calling workflow. The application supplies the user’s text and renders the returned structured fields. A local deterministic fallback runs when the model service is unavailable. A final safety gate can override a mild model label for an obvious hazard.

Model choice

The configured model is gpt-5.6-luna, accessed through OpenAI-compatible routing with Portkey when configured. The model was selected because it is the course-required project model and can return structured natural-language analysis. This report does not claim a measured superiority over other models.

One real run

  1. The user pastes a health message.
  2. The callback rejects an empty message.
  3. The app sends the text with instructions not to diagnose and to use the five exact labels.
  4. The response is parsed and normalized.
  5. Safety logic checks for obvious high-risk patterns.
  6. The app displays the category, explanation, next step, and sources.

6. Safety

What could go wrong?

  • The model could invent evidence or misclassify a claim.
  • A user could treat the result as diagnosis or delay urgent care.
  • Prompt injection could ask the model to ignore its role or reveal hidden instructions.
  • A repeated or automated request could overspend the API budget.
  • A dangerous claim could receive a reassuring label.

Defenses in the app

  • The system instruction says not to diagnose and requires exact categories.
  • The interface includes a safety note recommending urgent care for severe or sudden symptoms.
  • Structured JSON parsing and label normalization reduce presentation errors.
  • A local fallback prevents the app from failing silently when the API is unavailable.
  • A deterministic safety gate forces High caution for explicit biohazard examples such as sitting in a decomposing whale carcass.
  • Keys are loaded from environment variables and are not hard-coded.

Defense test

The biohazard test message is expected to return High caution and “Be careful with this advice,” even if a model response is milder.

8. Limits + next steps

What does not work yet?

  • The app is not a clinical decision tool and cannot personalize advice safely for every medical condition.
  • Model outputs and sources still require review; the fallback is intentionally limited.
  • There is no measured token/cost dataset in this draft.
  • There is no documented pilot with older adults in this draft.
  • The current checkpoint checks text only and does not analyze images or videos.
